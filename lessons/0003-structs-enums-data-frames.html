Lesson 03 · Rust data modeling

结构体、枚举与数据帧

把分散的 UART 配置整理成有名字的类型，再用枚举描述帧的不同状态。你会开始让编译器检查“哪些状态可能出现”，为后续所有权、借用和错误处理打基础。

时长 约 2–3 小时主题 struct、enum、match、借用读取完成标准 配置与帧模型可构建并通过 ARM 检查

本课成果：完成一个固定长度数据帧模型，能打印 UART 配置、匹配 8N1/8E1/8O1，并对数据帧和错误帧分别处理。

开始前，先回忆

不查资料，先回答两个问题：第 2 课为什么用 [...].contains(&baud)，而不是把四个数字写成一个元组？如果帧格式不是 8N1，上一课的 custom 代表什么？

完成回忆后查看要点

数组表示一组可以逐个检查的候选值，元组是一个固定结构的整体；custom 只是练习代码中对“不是 8N1”的标签，并没有描述具体是哪一种帧。本课把这些分散的值放进有名字的类型。

先选择合适的类型

  • 结构体 struct：多个字段总是一起描述一个对象，例如波特率、数据位和停止位共同组成 UART 配置。
  • 枚举 enum：一个值只能是若干变体中的一个，例如无校验、偶校验或奇校验。
  • match：根据枚举的变体执行不同分支；编译器会检查所有可能的变体是否处理完整。

这比用多个字符串和布尔值更可靠：Parity::Even 是受类型约束的状态，不能误写成任意字符串。Rust 官方把结构体视为组合相关数据的自定义类型，把枚举视为列出可能变体的自定义类型。

主阅读材料：Rust 官方《The Rust Programming Language》的结构体章节、枚举章节和match章节。

任务 A：把 UART 配置建模成类型

继续使用 case/uart_config。先定义校验方式和配置结构体：

#[derive(Debug, Clone, Copy)]
enum Parity {
    None,
    Even,
    Odd,
}

#[derive(Debug, Clone, Copy)]
struct UartConfig {
    baud: u32,
    data_bits: u8,
    stop_bits: u8,
    parity: Parity,
}

Parity::None 这样的写法明确指出了枚举变体。derive 让编译器自动生成调试打印和小型值的复制能力；本课先把它当作工具使用，所有权细节在下一课展开。

  1. 删除 main 中分散的 data_bits、stop_bits 和 parity 绑定。
  2. 创建一个 UartConfig 实例，使用 baud: 115_200、data_bits: 8、stop_bits: 1 和 parity: Parity::None。
  3. 用 println!("{config:?}") 观察结构体的调试输出。

任务 B：用 match 生成帧标签

把第 2 课的条件判断改造成函数。注意这里传入的是配置的借用，暂时不会取得配置的所有权：

fn frame_label(config: &UartConfig) -> &'static str {
    match (config.data_bits, config.parity, config.stop_bits) {
        (8, Parity::None, 1) => "8N1",
        (8, Parity::Even, 1) => "8E1",
        (8, Parity::Odd, 1) => "8O1",
        _ => "custom",
    }
}

这里的 match 匹配一个三元组：数据位、校验方式、停止位。下划线分支覆盖其他组合，因此函数始终有返回值。

  1. 在 main 中打印 frame_label(&config)，确认默认配置得到 8N1。
  2. 把校验方式改成 Parity::Even，预测并确认得到 8E1。
  3. 把数据位改成 7，确认得到 custom。

任务 C：让 enum 描述数据帧状态

固定长度的四字节载荷足够练习类型建模，也不会提前引入堆和 Vec：

#[derive(Debug)]
enum Frame {
    Data { sequence: u16, payload: [u8; 4] },
    Error { code: u8 },
}

fn frame_summary(frame: &Frame) -> (&'static str, usize) {
    match frame {
        Frame::Data { payload, .. } => ("data", payload.len()),
        Frame::Error { .. } => ("error", 0),
    }
}

Frame::Data 和 Frame::Error 是同一个类型的两种状态。.. 表示这个分支不关心其他字段；&Frame 表示只读取帧，不把它移动进函数。

  1. 创建一个 Frame::Data，序号为 1，载荷为 [0x55, 0xAA, 0x01, 0x00]。
  2. 创建一个 Frame::Error { code: 2 }。
  3. 分别调用 frame_summary(&data_frame) 和 frame_summary(&error_frame)，打印返回的类别和长度。
  4. 临时删除 Frame::Error 分支并运行 cargo check，阅读编译器的 non-exhaustive patterns 错误，然后恢复它。

任务 D：整合并在两个目标上检查

把配置、标签函数、帧枚举和摘要函数放进同一个 src/main.rs。主程序至少输出：

config=UartConfig { ... }
frame=8N1
data: 4 bytes
error: 0 bytes

输出中的结构体字段具体排版由调试格式决定，不必逐字符相同；关键是配置、帧标签和两种帧状态都出现。

cargo fmt
cargo check
cargo run --target x86_64-unknown-linux-gnu
cargo build --release
file target/armv7-unknown-linux-gnueabihf/release/uart_config

本课不要求把帧发送到真实 UART。先让同一份类型模型在 AMD64 主机和 PYNQ-Z2 的 ARMv7 目标上通过编译。

验收清单

  • 能说明结构体字段为什么比元组位置更适合描述 UART 配置。
  • 能区分 Parity::None 这样的枚举变体和任意字符串。
  • 能使用 match 同时匹配值和枚举变体，并处理通配分支。
  • 能解释 &UartConfig 和 &Frame 表示只借用读取，而不是取得所有权。
  • 删除一个 match 分支后，能读懂编译器关于未覆盖状态的提示并恢复完整匹配。
  • 主机运行、cargo check 和 ARMv7 release 构建都成功。
常见错误与定位方向
  • use of undeclared type：检查类型名和枚举变体是否使用大写开头，并确认定义在调用前。
  • non-exhaustive patterns：match 漏掉了枚举变体或没有使用覆盖其他情况的 _。
  • cannot move out of：函数参数可能拿到了值的所有权；本课读取结构体时使用 &UartConfig 或 &Frame。
  • doesn't implement Debug：打印 {:?} 的类型需要添加 #[derive(Debug)]。
